Assess the current repo's architecture: what is there and what is wrong with it. Change
no code. The only file you may write is an ADR (see *ADRs*).

## Before you start

1. If `.agents/onboarding.md` starts with `<!-- Generated by onboard:`, read its Index
   and Relationships.
2. If not, suggest the `onboard` skill. If the user declines, start from the manifests,
   entry points, top-level folders, and any README or design notes.
3. Read the key files; never assess from the report alone.

## Called by `onboard`

Skip *Before you start* and do not read `.agents/onboarding.md`; `onboard` has read the
key files. Return to `onboard` only technical debt and red flags, each tied to a
`file:line`. Print and write nothing.

## Review

### 1. Current state

- Structure: the main parts, what each does, how they connect.
- Patterns and conventions the code already follows.
- Technical debt: duplication, dead code, outdated dependencies, missing tests,
  workarounds.
- Limits to growth: scale, performance, deployment, team size.

### 2. Requirements

Ask only what the code cannot tell you: the goal; non-functional needs (performance,
security, scalability, availability); integration points and data flow to respect.

### 3. Design proposal

Only when the user wants a change designed: the parts and what each owns, data models
and API contracts, how the parts connect.

### 4. Trade-offs

For each design decision: pros, cons, alternatives considered, and the decision with its
reason.

## Principles

- **Modularity**: one job per part, high cohesion, low coupling, clear interfaces.
- **Scalability**: stateless where possible, efficient queries, caching where it pays.
- **Maintainability**: consistent patterns, easy to test and understand.
- **Security**: least privilege, input checked at the boundaries, safe by default.
- **Performance**: no needless work or network calls.

## System design checklist

For a new system or feature; skip lines that do not apply.

- Functional: user stories, API contracts, data models, main flows.
- Non-functional: latency and throughput targets, scale, security, uptime.
- Technical: part responsibilities, data flow, integration points, error handling,
  test strategy.
- Operations: deployment, monitoring and alerts, backup and recovery, rollback.

## Red flags

Report each one you find:

- **Big Ball of Mud**: no clear structure.
- **Golden Hammer**: one solution for everything.
- **Premature optimization**: speed work before it is needed.
- **Not Invented Here**: rejecting existing solutions.
- **Analysis paralysis**: much planning, little building.
- **Magic**: unclear or undocumented behavior.
- **Tight coupling**: parts too dependent on each other.
- **God object**: one class or module that does everything.

## Report

In chat: current structure, technical debt, red flags, in that order, the risks that
matter most first. Keep it short. Never save it to a file, `.agents/onboarding.md`
included; findings go stale faster than maps. Tie every finding to its file
(`path:line` when you can); drop any you cannot.

## ADRs

Only when the user makes a decision:

1. Find the repo's ADR folder: `docs/adr/`, `adr/`, or `docs/decisions/`. If there is
   none, ask where to put it before writing.
2. Match the existing ADRs' format and numbering.
3. Record the context, decision, alternatives, and consequences.
