---
name: codemap
description: Map a codebase into short, token-lean architecture docs in `docs/CODEMAPS/`, with an ASCII graph of the whole repo. Use when the user says "map this codebase", "generate codemaps", "update the codemaps", or wants a fast overview of how a repo fits together before working in it.
---

Write a small set of maps that tell a reader, human or agent, how this repo is
laid out. A script collects the facts. You read the key files and write the
maps. The maps are committed in the target repo.

## 1. Collect facts

Run the script in this skill's own folder (next to this file):

```
python3 <this skill folder>/facts.py [ROOT]
```

`ROOT` is the repo to map; it defaults to the current directory. The script
needs Python 3.11 or newer, writes nothing, and prints Markdown: languages,
manifests with their dependencies, entry points, a folder tree, and the docs
that exist. Paths are relative to `ROOT`.

If it fails, say so and carry on by listing files with your own search tools.

## 2. Read the key files

The facts say where to look. They are not the map. Read before you write:

- the entry points it lists
- the manifests (scripts, dependencies)
- the biggest or most central folders: open a few files in each
- existing docs it lists (README, `AGENTS.md`, ADRs); skim them and use them as
  hints, but check claims against the code

Use your search tools to find routes, handlers, models, migrations, components,
and imports. Note the file where you saw each thing.

## 3. Choose the maps

Write only the maps this repo needs. Never create an empty or padded map. If an
area does not exist, skip its file.

| File | Write it when the repo has | Contents |
|---|---|---|
| `INDEX.md` | always | ASCII graph of the whole repo, links to the other maps |
| `architecture.md` | more than one module or service | system diagram, boundaries, data flow |
| `backend.md` | an API, server, CLI, or job runner | routes or commands, middleware chain, service to storage mapping |
| `frontend.md` | a UI | page tree, component hierarchy, state flow |
| `data.md` | a database, schema, or migrations | tables, relationships, migration history |
| `dependencies.md` | external services or notable libraries | what each is for, version, where it is used |

Use only these six file names. Fold anything else into the closest one: helper
scripts and runtime tooling go in `backend.md`, or in `architecture.md` if the
repo has no backend.

Decide by what you read, not by folder names. A folder called `hooks/` may hold
git hooks, not React hooks. An `.ico` file is not a module.

## 4. Write the maps

Put them in `docs/CODEMAPS/` in the target repo. Every map starts with this
exact first line, with today's date:

```
<!-- Generated by codemap: YYYY-MM-DD -->
```

Keep each map under about 1000 tokens. Favour:

- file paths and function signatures, not code blocks
- one line per item: `src/services/user.ts (business logic, 120 lines)`
- ASCII diagrams for flow, not long prose
- the shape of the system, not every detail

Example of a good `backend.md` body:

```
# Backend

## Routes
POST /api/users -> UserController.create -> UserService.create -> UserRepo.insert
GET  /api/users/:id -> UserController.get -> UserService.findById

## Key files
src/services/user.ts (business logic, 120 lines)
src/repos/user.ts (database access, 80 lines)

## Dependencies
- PostgreSQL (primary store)
- Redis (sessions)
```

### The graph in `INDEX.md`

Draw one ASCII box-and-arrow graph of the whole repo from what you read.

- Draw only edges you saw in a file. Do not guess.
- Under the graph, add a legend with one line per edge that names the file:
  `A -> B  (src/a.py imports b)`.
- If you could not confirm an edge, leave it out.

Then add links to every other map you wrote, and the date.

## 5. Re-runs

Look at what is in `docs/CODEMAPS/` first; the script's Docs section marks each
file `generated` or `hand-written`.

- A file with the generated header may be updated.
  - If the user asked for the maps directly ("update the codemaps"), that is the
    yes: update them, then list which maps changed and what is new, removed, or
    different.
  - If the update comes up as a side effect of another task (for example during
    onboarding), first tell the user in a few lines what would change, and ask.
    Write only after a yes.
- A file without that header is not yours, even if the user asked for an update.
  Never edit, overwrite, rename, or delete it. Report it
  ("`docs/CODEMAPS/backend.md` is hand-written; left alone") and, if a map is
  needed under that name, ask the user what to do.
- If nothing changed, say so and write nothing.

## 6. Finish

List the files you wrote and the areas you skipped, with the reason. Suggest the
user commit `docs/CODEMAPS/`. Run the script again after big refactors or new
features to refresh the maps.
