---
name: onboard
description: Get to know an unfamiliar repository. Writes one report that maps the codebase as an index of its parts, an ASCII graph of how they relate, and a section per part, then lets the user dive into any part or name a task. Use when the user says "onboard me", "onboard this repo", "help me understand this codebase", "map this codebase", "give me an overview of this repo", "how does this repo fit together", or opens a repository they have not worked in before.
---

Write one report a reader can take in at a glance and then dive into: an **index** of
the repo's parts, a **graph** of how they relate, and a **section** per part, all tied
by the same `[n]` numbers.

```
facts ──▶ read key files ──▶ risks ──▶ report ══ stop and ask ══▶ deep dive or task
facts.py                     architect  .agents/onboarding.md
```

## 1. Collect facts

Run the script next to this file:

```
python3 <this skill folder>/facts.py [ROOT]
```

It needs Python 3.11+, writes nothing, and prints Markdown: languages, manifests and
dependencies, entry points, a folder tree, docs, and the status of the report file. If
it fails, say so and list files with your own search tools.

## 2. Read the key files

The facts say where to look; they are not the map. Read the entry points, the
manifests, a few files in each large or central folder, and the README, `AGENTS.md`,
and ADRs (as hints; check claims against the code). Note the `file:line` where you saw
each thing. Decide by what you read, not by folder names: a `hooks/` folder may hold git
hooks, not React hooks.

## 3. Find risks

Follow the `architect` skill in its *Called by `onboard`* mode. It returns risks, each
tied to a `file:line`, and prints nothing itself.

## 4. Write the report

Split the repo into **components**: a file, folder, or `file:line-range` with one job
(an entry point, a module, a config tree, the test suite). At most 12. If there are
more, group related ones into one entry and list its members, unnumbered, in that
entry's Key files.

Write `.agents/onboarding.md` in this shape:

```
<!-- Generated by onboard: YYYY-MM-DD -->
# <repo> — onboarding

<2–3 lines: what the repo is for, how it runs, how it is tested.>

## 1. Index

[1] <Name> — `<key file>` — <one-line purpose>
[2] …

## 2. Relationships

[1] ──runs──▶ [2] ──imports──▶ [3]
                 └─writes──▶ (Postgres)

- [1] → [2] runs — `<file:line>`
- [2] → [3] imports — `<file:line>`

## 3. Sections

### [1] <Name>
What: <what it does, one or two lines>
Key files: `<path>` (<role>), …
Read first: `<path>`
```

- The Index lists what exists. Only the graph shows how parts relate; sections never
  repeat it.
- Every arrow carries a verb and has one legend line citing the `file:line` that shows
  it. Draw only edges you saw in a file. Things outside the repo (a database, an API,
  `~/.config`) may appear unnumbered in parentheses, with no section.
- The set of `[n]` is the same in the Index, the graph, and Sections. A part with no
  edges still appears in the graph, alone on its own line.
- No risks in the file: it may be public, and risks go stale.

### The file

- If `.agents/onboarding.md` starts with the generated header, rewrite it and list
  what changed since the last version.
- If it exists without the header, it is not yours: never edit, rename, or delete it.
  Ask the user where to write. If you cannot ask, write nothing and give the report in
  chat only.

## 5. Report in chat, then stop

Print the whole report as written, legend and Key files included, with two additions:

- under each section, `Risks:` from step 3 that belong to that part only
- after the sections, `Across parts:` at most 3 risks that span several parts or none,
  each naming its parts and files

Say where the file was written. Then ask: **"Pick a number to dive in, or name a
task."** Do not go on until the user answers. Do not invent a task.

## 6. Deep dive or task

- **A number:** read that part's files in depth; show how data or control moves through
  it, with `file:line`; list its risks with evidence; draw a small graph of it and its
  direct neighbours if that helps. Chat only; change no file. End by asking what to work
  on.
- **A task:** start from the parts it touches and their Key files.

## Rules

- The repository's own `AGENTS.md` or `CLAUDE.md` overrides anything here.
- Write only `.agents/onboarding.md`. Ignore old `docs/CODEMAPS/` maps: do not use
  them as input, and do not delete them.
- Do not run the project's tests, builds, or installs. Say how the project is tested
  instead.
- If `architect` is not installed, say so and list the risks yourself, each with its
  `file:line`.
